# 分类 B:分类 A 在本项目场景下的特化

> **分类 A**(Barr et al. 2015, *The Oracle Problem in Software Testing: A Survey*)
> 把 oracle 按**来源**分成四大类。它是通用的,不针对任何具体场景。
>
> **分类 B** 不另起炉灶,它就是分类 A 的那几类,外加三件分类 A 不会回答的事:
>
> 1. **在我们的场景里,这一类拿不拿得到?**(有些类在 Python 生态里根本不存在,
>    有些被我们刻意禁用)
> 2. **agent 实际用了多少?**(85 次运行的实测)
> 3. **每个 CVE 需要哪一类?** 需要的和实际用的对不上,就是没命中的原因。
>
> 换句话说:**分类 A 说 oracle 可以从哪来;分类 B 说在这里哪些来得了、来了多少、
> 以及每个样本缺的是哪一类。**

---

## 0. 分类 B 在整个框架里的位置

一次 PBT 检测要连过五道门,任何一道过不去整条就断:

```
1 生成 I2  →  2 到达 I3  →  3 发生 I5  →  4 观察 I4  →  5 判断 I1
```

**分类 B 展开的是最后那一道门 I1。** I1 问「有没有依据判定对错」,
分类 B 回答「那个依据属于 A 的哪一类、拿不拿得到」。

I2 到 I5 不是 oracle 问题(抽样、前置状态、可观测性),不归分类 B 管。
这是上一版做错的地方——上一版把五道门都塞进了分类 B,等于让一个 oracle 分类
去回答非 oracle 的问题,也就把分类 A 架空了。

## 1. 分类 A 的各类在本场景的可得性

| 分类 A 的类别 | 在本场景 | 实测用量(85 次运行) |
|---|---|---|
| **Specified 4.1** 形式规约语言 | ✗ 不存在。Python 生态基本没有形式规约 | 0 |
| **Specified 4.2** 断言与契约 | △ 少量。源码里的 `assert`、类型注解 | 少量,与 4.3 混用 |
| **Specified 4.3** 代数规约 | ✓ **主力之一**。往返、幂等、交换、合流 | **43/85**,9 个样本 |
| **Derived 5.1** 伪 oracle(双实现对拍) | ✓ 可得,但**几乎不用** | **9/85**,4 个样本 |
| **Derived 5.2** 蜕变关系 | ✓ 可得 | 10/85,4 个样本 |
| **Derived 5.3** 回归测试套件 | ✗ **我们刻意禁用** —— 见下 | 0 |
| **Derived 5.4** 执行轨迹 | ✗ 不适用 | 0 |
| **Derived 5.5** 文本文档(docstring) | ✓ **主力**。`hypo.md` 的铁律指的就是这一类 | 大部分运行 |
| **Implicit** 隐式(崩溃、挂起、内存错误) | ✓ **不需要任何规约**,最廉价 | **26/85**,6 个样本 |
| **Human** 人 | ✗ 要自动化,用不了 | 0 |

**5.3 为什么被禁用。** 修复提交几乎总会同时改它自己的回归测试。那些测试就是答案本身。
`enrich_functions.py` 里的 `is_test_path()` 专门把它们排除掉,否则等于把标准答案
交给 agent。这是本场景相对分类 A 的一处**主动约束**,不是能力不足。

## 2. 一个贯穿性的发现:提示词只覆盖了隐式类的一半

分类 A 的 **Implicit** 类包含两种征兆:**崩溃**和**挂起**。

`hypo.md` 的八种模板里,对应隐式类的只有一条:

> **Single entry point**: ... test that calling it on valid inputs **doesn't crash**

**只有崩溃,没有挂起。**

而 ReDoS 这一整类缺陷,它的 oracle 恰恰是隐式类里的**挂起**——不需要任何规约,
跑得太慢本身就是错。但模板里没有这一条,于是 agent 得自己想到。

六个 ReDoS 样本的实测,就是这条缺口的后果:

| 样本 | 用过隐式 oracle(耗时) | 结果 |
|---|---:|---|
| black | 5/5 | **稳定命中 5/5** |
| dparse | 5/5 | **稳定命中 5/5** |
| pygments | 5/5 | **稳定命中 5/5** |
| configobj | 4/5 | 不稳定 3/5 |
| cleo | 2/5 | 不稳定 2/5 |
| soupsieve | **0/5** | **从未命中 0/5** |

**完全对齐。** 而 soupsieve 并不是没测对地方——它五次都写了往返测试(4.3 代数),
输入也造对了(重复 2000 次的嵌套前缀),但断言是「只抛出文档里写明的异常」,
还主动关掉了 Hypothesis 自带的超时检查(`deadline=None`)。

**它在 5.5 和 4.3 两类里找 oracle,而这个缺陷的 oracle 在 Implicit 类里。**

## 4. 三个从未命中的样本,是三种不同的失配

### soupsieve —— **找错了类别**

需要 Implicit(挂起),它只在 4.3 和 5.5 里找。
**oracle 是存在的、而且是最廉价的那一类,只是没被想到。**

→ **可修,且改提示词就能验证。** 把隐式类的「挂起」补进模板。
black / dparse / pygments 证明这条路走得通,差别只在那一行 `assert elapsed < 1.0`。

### eml-parser —— **该用的类别从未被使用过**

「URL 提取应当不受 HTML 实体编码影响」这句话,源码里任何地方都没有。
5.5 这一类在这里是空的。

但它**不是无解**:可以拿另一个 HTML 解析器对拍——这正是 **5.1 伪 oracle**。
而全部 85 次运行里,对拍只用了 **9 次**,eml-parser 一次没用。

→ **可修,但要做的是让 5.1 真正可用**(怎么选参考实现、怎么处理两边都错的情况),
不是加一行提示词。

### lxml-html-clean2 —— **oracle 真的不存在**

「清洗后不应残留 `<base>` 标签」——源码没写,没有参考实现(其他清洗库的策略各不相同),
不是代数性质,也不是隐式征兆(不崩溃、不挂起、返回值合法)。

grep 到的 `base` 只是它随机标签列表里的一项,断言全是关于 javascript 协议的,
**等于从未提出**。

→ **分类 A 的各类在这里全部落空。** 要测它,得引入外部规约(安全基线、同类库的策略文档)。
这是研究问题,不是工程问题。

## 5. 证据强度

| 结论 | 证据 | 强度 |
|---|---|---|
| ReDoS 的 oracle 在 Implicit 类,用了就中、没用就不中 | 6 个样本组内对照,完全对齐 | **强** |
| 模板覆盖了「崩溃」但漏了「挂起」 | 直接读 `hypo.md` 第 82 行 | **强**(文本事实) |
| 5.1 伪 oracle 严重欠用 | 9/85 次运行,4/17 个样本 | **中** |
| 5.5 落空 → 必然失败 | 2 个样本(eml-parser、lxml-html-clean2) | **中**,n=2 |
| 5.3 必须禁用 | 设计决策,非实测 | — |

**本分类目前只能解释失败,还不能预测成功。** 要预测,得有一个事前能算的量回答
「这个 CVE 的 oracle 在 A 的哪一类」。现在这一栏是人工判的。

## 6. 下一步

1. **把「挂起」补进模板,拿 soupsieve 跑 5 次验证。** 它 0/5,信号最干净,
   约 $3。这是全部工作里投入产出比最高的一项。
2. **让 5.1 伪 oracle 真正可用。** 现在八种模板里有「双实现对拍」这一条,
   但 85 次运行只用了 9 次。先查清是没想到,还是找不到参考实现。
3. **把「需要哪一类 A」变成可计算的。** 一个可能的做法:看补丁改的是什么——
   改复杂度 → Implicit 挂起;改返回值且文档有描述 → 5.5;改的是编码/解析的
   等价类 → 5.1 对拍。
4. **psd-tools 定类。** 它写过尺寸断言(`assert len(out) == w*h*d//8`),
   但用的是往返测试,这种写法从构造上就产生不了 ZIP 炸弹——要触发得直接生成
   压缩流。查那 2 次命中的运行怎么构造的输入才能定。
